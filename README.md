# Универсальный шаблон проекта

Этот репозиторий задаёт общие правила работы, качества, тестирования, безопасности и развёртывания. Он не содержит приложения и не выбирает за команду язык, framework, runtime, базу данных, хостинг или тестовый инструмент. Конкретные технологии и команды фиксируйте только после выбора стека для создаваемого проекта.

## Начало работы с шаблоном

1. Скопируйте шаблон в репозиторий проекта и сохраните `AGENTS.md`, профильные документы и необходимые профили `.codex/agents/`.
2. До реализации создайте `tickets/<ID>-<slug>/TASK.md` по правилам [`tickets/README.md`](tickets/README.md). Укажите требования, проверяемую приёмку и допущения.
3. Для нового приложения или изменения эксплуатации выберите целевой профиль в `DEPLOYMENT.md`: локальный прототип/MVP, кандидат в production или production. Не трактуйте локальные проверки как подтверждение production-готовности.
4. Определите стек и целевые окружения по требованиям задачи. Заполните применимые документы фактическими решениями и командами; не оставляйте шаблонные заглушки как описание уже реализованных функций.
5. Назначайте роли по `AGENTS.md`. Разработчики реализуют production-код; `unit-tester` создаёт и обновляет unit-тесты и запускает полный набор; `ui-tester` отвечает за применимые UI/E2E-проверки.

## Основные документы

- [`AGENTS.md`](AGENTS.md) — порядок работы, обязательные роли и передачи.
- [`CONTRIBUTING.md`](CONTRIBUTING.md) — разработка, проверки и review.
- [`CONVENTIONS.md`](CONVENTIONS.md) — стек-независимые критерии читаемости и архитектурных границ.
- [`TESTING.md`](TESTING.md) — уровни тестирования, владельцы, команды и отчёты.
- [`SECURITY.md`](SECURITY.md) — общие требования безопасной разработки.
- [`DEPLOYMENT.md`](DEPLOYMENT.md) — целевые профили и требования к готовности окружения.
- [`API.md`](API.md) — контракт API, если у приложения есть API.
- [`prototypes/README.md`](prototypes/README.md) — UX/UI-прототипы для видимых изменений.
- [`tickets/README.md`](tickets/README.md) — папки задач и артефакты.

Правила намеренно соразмерны масштабу и риску проекта. Неприменимые уровни, компоненты и инфраструктуру не нужно добавлять искусственно; их неприменимость или ограничения фиксируются в задаче и review.
