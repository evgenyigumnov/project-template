# Правила работы субагентов

Перед каждой задачей определи затронутые области и запусти как минимум одного подходящего субагента из списка. Передавай ему ограниченную подзадачу с ожидаемым результатом и дождись отчёта. Крупную задачу в пределах одной специализации разбивай на этапы: запускай профильного субагента отдельно для каждого этапа и последовательно — следующий запуск начинай после отчёта предыдущего, передав ему нужный контекст, изменённые пути, решения и открытые вопросы. Для междисциплинарных задач подключай владельцев нужных областей; зависимую работу выполняй последовательно, независимые проверки можно распараллелить. Если подходящего профиля нет, выбирай ближайший по типу работы: analyst для требований и анализа, frontend-developer или backend-developer для реализации, code-reviewer для независимой проверки. Главный агент координирует работу и сводит результаты. Не коммить и не отправляй изменения без прямой просьбы пользователя.

| Субагент | Ответственность за файлы |
| --- | --- |
| analyst | DOMAIN.md, BUSINESS_RULES.md, REQUIREMENTS.md, GLOSSARY.md, tickets/*/ANALYSIS.md |
| architector | ARCHITECTURE.md, CONVENTIONS.md, docs/adr/*.md, docs/DESIGN.md |
| frontend-developer | исходный код клиентской части, UI, клиентское состояние и frontend-специфичные конфигурация, сборка, зависимости и package.json |
| backend-developer | исходный код серверной части, серверная логика и API-контракт в API.md; backend-специфичные конфигурация, сборка, зависимости и package.json |
| database-developer | DATABASE.md, SQL-файлы, миграции БД, docs/DB_PERFORMANCE.md |
| devops | DEPLOYMENT.md, инфраструктурные конфигурации, серверы, кластеры, CI/CD и развёртывание |
| security-engineer | SECURITY.md, tickets/*/SECURITY_REVIEW.md, анализ безопасности кода и конфигураций |
| ux-ui-expert | prototypes/**, docs/UI_GUIDELINES.md, docs/USER_FLOWS.md |
| unit-tester | TESTING.md, unit-тесты, docs/UNIT_TESTING.md |
| ui-tester | раздел UI/E2E в TESTING.md, UI/E2E-тесты, docs/UI_TESTING.md |

## Структура проекта и общие артефакты

### Что есть в репозитории сейчас

| Путь | Назначение |
| --- | --- |
| `AGENTS.md` | Общие правила, карта ответственности и порядок взаимодействия. Используют все субагенты. |
| `.codex/agents/*.toml` | Профили и инструкции специализированных субагентов. |
| `API.md` | Контракт API: общие правила, авторизация, форматы запросов и ответов, ошибки и описание endpoint-ов; владелец — backend-developer. |
| `CONTRIBUTING.md` | Правила разработки, PR, коммитов и code review; владелец — code-reviewer. |
| `CONVENTIONS.md` | Соглашения о стиле кода, именовании и технических паттернах; владелец — architector. |
| `DEPLOYMENT.md` | Сборка, CI/CD, окружения и развёртывание; владелец — devops. |
| `SECURITY.md` | Требования безопасности, авторизация, секреты и запрещённые операции; владелец — security-engineer. |
| `TESTING.md` | Общая стратегия тестирования, команды запуска и требования к покрытию; владелец — unit-tester, раздел UI/E2E ведёт ui-tester. |
| `README.md` | Файл описания проекта; сейчас содержит только заголовок. |
| `LICENSE` | Лицензия проекта. |

### Где хранить общий контекст

| Путь | Что там хранится и как используется |
| --- | --- |
| `tickets/<номер>/` | Контекст конкретной задачи: описание, материалы и результаты работы. Все участвующие субагенты читают относящиеся к задаче материалы; `ANALYSIS.md` ведёт analyst, `CODE_REVIEW.md` — code-reviewer, `SECURITY_REVIEW.md` — security-engineer. |
| `DOMAIN.md`, `BUSINESS_RULES.md`, `REQUIREMENTS.md`, `GLOSSARY.md` | Общие сведения о предметной области и требованиях. Это постоянный источник контекста для analyst, architector, frontend-developer, backend-developer и тестировщиков. |
| `API.md`, `ARCHITECTURE.md`, `DATABASE.md` | Актуальные API-контракт, архитектура и схема данных; backend-developer, architector и database-developer поддерживают свои документы, остальные сверяются с ними перед изменениями. |
| `CONTRIBUTING.md`, `CONVENTIONS.md` | Общие правила взаимодействия при разработке и технические соглашения; code-reviewer и architector поддерживают их в своих областях, все разработчики следуют им. |
| `DEPLOYMENT.md`, `SECURITY.md` | Правила эксплуатации и развёртывания, требования безопасности и запрещённые операции; владельцы — devops и security-engineer соответственно. |
| `TESTING.md` | Общая стратегия и правила тестирования; unit-tester поддерживает документ, ui-tester отвечает за раздел UI/E2E. Остальные участники сверяются с ним при изменениях и проверках. |
| `docs/` | Тематическая документация: `docs/adr/` — решения по архитектуре; остальные файлы `docs/` — правила дизайна, UI, тестирования, БД и ревью согласно таблице ответственности выше. |
| `prototypes/` | Прототипы интерфейсов и UX-контекст для дизайна, реализации и UI-проверок. |
| Каталоги исходного кода, тестов и миграций | Расположение определяется фактической структурой приложения и его конфигурацией; не предполагай имена каталогов, пока их нет в проекте. |

### Передача контекста между субагентами

- Перед началом работы прочитай описание задачи и относящиеся к ней общие документы, включая применимые `CONTRIBUTING.md`, `CONVENTIONS.md`, `DEPLOYMENT.md`, `SECURITY.md`, `TESTING.md` и `API.md`. Если в `tickets/<номер>/` уже есть анализ, отчёт ревью или `SECURITY_REVIEW.md`, используй их как контекст.
- Сохраняй устойчивые требования, решения и результаты в предназначенных для них общих файлах, указанных выше и в таблице ответственности. Не оставляй важные решения только в переписке и не дублируй один документ в нескольких местах.
- При передаче работы укажи изменённые пути, кратко опиши принятое решение и открытые вопросы; при необходимости добавь ссылки на профильные документы в материалы тикета.
- Обновляй эту карту, когда в проекте закрепляется новая общая папка или меняется расположение документов. Содержание самих требований и решений храни в профильных документах, а не в `AGENTS.md`.
