# Правила работы субагентов

Перед каждой задачей определи затронутые области и запусти как минимум одного подходящего субагента из списка. Передавай ему ограниченную подзадачу с ожидаемым результатом и дождись отчёта. Для междисциплинарных задач подключай владельцев нужных областей; зависимую работу выполняй последовательно, независимые проверки можно распараллелить. Если подходящего профиля нет, выбирай ближайшего по типу работы: analyst для требований и анализа, programmer для реализации, code-reviewer для независимой проверки. Главный агент координирует работу и сводит результаты. Не коммить и не отправляй изменения без прямой просьбы пользователя.

## Субагенты и ответственность за файлы

| Субагент | Ответственность за файлы |
| --- | --- |
| analyst | DOMAIN.md, BUSINESS_RULES.md, REQUIREMENTS.md, GLOSSARY.md, tickets/*/ANALYSIS.md |
| architector | ARCHITECTURE.md, docs/adr/*.md, docs/DESIGN.md |
| programmer | исходный код, конфигурация приложения, файлы сборки и зависимостей, package.json |
| ux-ui-expert | prototypes/**, docs/UI_GUIDELINES.md, docs/USER_FLOWS.md |
| unit-tester | unit-тесты, docs/UNIT_TESTING.md |
| ui-tester | UI/E2E-тесты, docs/UI_TESTING.md |
| db-expert | DATABASE.md, SQL-файлы, миграции БД, docs/DB_PERFORMANCE.md |
| code-reviewer | docs/CODE_REVIEW.md, tickets/*/CODE_REVIEW.md |

## Структура проекта и общие артефакты

### Что есть в репозитории сейчас

| Путь | Назначение |
| --- | --- |
| `AGENTS.md` | Общие правила, карта ответственности и порядок взаимодействия. Используют все субагенты. |
| `.codex/agents/*.toml` | Профили и инструкции специализированных субагентов. |
| `README.md` | Файл описания проекта; сейчас содержит только заголовок. |
| `LICENSE` | Лицензия проекта. |

### Где хранить общий контекст

| Путь | Что там хранится и как используется |
| --- | --- |
| `tickets/<номер>/` | Контекст конкретной задачи: описание, материалы и результаты работы. Все участвующие субагенты читают относящиеся к задаче материалы; `ANALYSIS.md` ведёт analyst, `CODE_REVIEW.md` — code-reviewer. |
| `DOMAIN.md`, `BUSINESS_RULES.md`, `REQUIREMENTS.md`, `GLOSSARY.md` | Общие сведения о предметной области и требованиях. Это постоянный источник контекста для аналитика, архитектора, программиста и тестировщиков. |
| `ARCHITECTURE.md`, `DATABASE.md` | Актуальные архитектура и схема данных; профильные субагенты обновляют их при соответствующих изменениях, остальные сверяются с ними. |
| `docs/` | Тематическая документация: `docs/adr/` — решения по архитектуре, остальные файлы `docs/` — правила дизайна, UI, тестирования, БД и ревью согласно таблице ответственности выше. |
| `prototypes/` | Прототипы интерфейсов и UX-контекст для дизайна, реализации и UI-проверок. |
| Каталоги исходного кода, тестов и миграций | Расположение определяется фактической структурой приложения и его конфигурацией; не предполагай имена каталогов, пока их нет в проекте. |

### Передача контекста между субагентами

- Перед началом работы прочитай описание задачи и относящиеся к ней общие документы. Если в `tickets/<номер>/` уже есть анализ или отчёты, используй их как контекст.
- Сохраняй устойчивые требования, решения и результаты в предназначенных для них общих файлах, указанных выше и в таблице ответственности. Не оставляй важные решения только в переписке и не дублируй один документ в нескольких местах.
- При передаче работы укажи изменённые пути, кратко опиши принятое решение и открытые вопросы; при необходимости добавь ссылки на профильные документы в материалы тикета.
- Обновляй эту карту, когда в проекте закрепляется новая общая папка или меняется расположение документов. Содержание самих требований и решений храни в профильных документах, а не в `AGENTS.md`.
